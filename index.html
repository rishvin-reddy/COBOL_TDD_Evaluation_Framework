1. Purpose

Define what the evaluation system must prove before a COBOL modernization workflow can be considered complete.

Core completion principle Project completion is not established by an LLM stating that the translation is correct. Completion is established by independently executable scenarios, coverage evidence, legacy-system outputs, converted-system outputs, and explicit validation results.
01
Discover business decisions and rules from the legacy system
02
Convert discovered rules into executable test scenarios
03
Compare legacy and converted behavior independently
04
Detect uncovered decision points and incomplete scenarios
05
Record complete traceability from source to test result
06
Produce evidence for customer/human validation

4. Business Logic Evaluation Layer

The primary objective is to prevent silently missing business rules.

Primary risk identified in the team experiment An AI-generated rule that is wrong can usually be detected by review or testing. A rule silently omitted by the AI is harder to detect because the output can still appear complete.

4.3 Independent Citation Verification

Pass

The cited COBOL lines independently support the rule description.

Fail

The cited source does not support the generated rule, the citation is invalid, or the relevant source cannot be verified.

Verifier independence requirement The citation verifier must not be the same model run, prompt, or context that drafted the rule. Acceptable configurations: a different model with no access to the draft's reasoning, deterministic checks (line existence, identifier/literal match), or human review. Where an LLM verifier is used, a defined sample of Pass and Fail decisions is spot-checked by a human, and the sampling rate and results are recorded (TDD-BIZ-007).

4.4 Coverage Principle

Coverage must be measured against discovered decision points. A successful test suite is not sufficient if the scenario generator silently omitted a business branch. The evaluation layer therefore compares the generated scenario set against the parser's structural decision-point inventory.

4.5 Decision Classification & Recall

Misclassification is a silent-omission path. Every parser-discovered decision point is classified as a business rule or a technical/control decision. A real business rule classified as technical disappears from the scenario set without any test able to fail. Classification is therefore evaluated for recall, not only for the precision of the rules that were kept.
  • Every decision point carries a classification and a written rationale; "unclassified" blocks Gate 2.
  • Every technical/control classification is listed in the review package, grouped by reason (file status, EIB/response check, loop control, etc.).
  • Seeded fixtures containing known business rules are classified during each release; any miss fails TDD-BIZ-006.
  • A human samples technical/control classifications, with a higher sampling rate for those touching amounts, limits, eligibility, status, or dates.
  • Parser completeness is reconciled against a raw construct count (IF, EVALUATE, PERFORM UNTIL, GO TO DEPENDING, etc.) so skipped constructs are visible (TDD-SRC-005).

Gate 1 — Source Readiness

1
Required source files discovered.
2
Required copybooks/dependencies available.
3
Parser can establish a valid structural representation.
4
Parser completeness is reconciled against an independent construct count (TDD-SRC-005).

Gate 2 — Business Logic Readiness

1
Decision points have been inventoried.
2
Proposed business rules have source evidence.
3
Citations have been independently verified.
4
Uncovered decision points are explicitly identified.
5
Every decision point is classified with rationale; classification recall passes; verifier independence is documented; external rule sources are reviewed or waived.

Gate 3 — TDD Readiness

1
Required scenarios exist.
2
Each scenario has an input and expected behavioral basis.
3
Scenarios can execute against the legacy system.
4
Outcome coverage meets configured thresholds; a legacy oracle exists for each in-scope program type (batch, online/CICS).

Gate 4 — Functional Equivalence

1
All required scenarios execute against the converted system.
2
Outputs are captured.
3
Configured non-semantic differences are normalized.
4
Business-significant differences fail evaluation.
5
COBOL fidelity tests (numeric, encoding, dates, layouts, error paths) are executed for in-scope programs.

Gate 5 — Security & Performance

1
Security checks complete.
2
No unresolved mandatory security findings.
3
Performance is measured against customer-approved thresholds.
4
Evidence contains no unmasked sensitive data.

Final Evaluation Gate

PASS requires all mandatory conditions to be satisfied.
  • Source is sufficiently parsed.
  • Business-rule evidence is traceable.
  • Coverage thresholds are met and every gap has a recorded disposition.
  • Classification recall passes and no decision point is unclassified.
  • Required scenarios execute.
  • Legacy and converted behavior satisfy equivalence criteria.
  • No unresolved mandatory security failure remains.
  • Performance requirements are satisfied where applicable.
  • Known gaps and limitations are explicitly reported.
FAIL / REWORK Any mandatory criterion that is not satisfied routes the artifact to the appropriate correction or human-review path rather than allowing the workflow to claim completion.

13. Human Review & Customer Validation

Automated Path

  • Run parser
  • Build decision inventory
  • Generate and verify rule records
  • Generate scenarios
  • Execute legacy oracle
  • Execute converted system
  • Compare outputs
  • Calculate coverage
  • Run security/performance checks

Human Path

  • Review unresolved exceptions
  • Review uncovered decision points
  • Review disputed business rules
  • Review security findings where required
  • Validate customer-specific expectations
  • Approve final evidence
Human review should focus on uncertainty. The framework is designed to reduce the amount of code and evidence that a person must manually inspect, while ensuring unresolved gaps are not hidden.
Approval criteria Approvers are named roles (for example business owner, COBOL SME, security reviewer) who are independent of the translation work. Each approval records what was reviewed: exceptions, gap dispositions, waived rules, normalization rules, and sampled classification decisions (TDD-APR-003).

14. Known Limitations

These limitations were explicitly identified during the team's investigation and should remain visible in the evaluation deliverable.

Limitation Impact Framework Response
Parser cannot read all legacy code Some source behavior may remain inaccessible. Log unreachable/unparsed code instead of treating it as empty or successful.
Copybooks may be required Parsing may be invalid without dependencies. Dependency readiness is an explicit gate.
Copybook expansion can shift line numbers Source citations can reference incorrect locations. A source-location correction/mapping layer is required.
Screen-based / CICS programs need a replay oracle Online transactions cannot be validated with simple batch replay; for CICS-heavy repositories this covers most programs. Build terminal/transaction replay (TDD-FUN-011) or explicitly classify unreplayed paths; gate 3 requires an oracle per program type.
Rules may exist outside source code Database tables or external configuration may contain business logic not visible in COBOL. Record the missing source of authority and require additional validation.
Legacy behavior may itself be incorrect Behavioral equivalence does not establish business correctness. Clearly distinguish behavioral equivalence from business-intent validation.
Scenario-generation errors Missing scenarios can hide missing business rules. Test the scenario generator itself against known fixtures and compare against parser-derived coverage.
Parser may silently skip constructs Skipped constructs never enter the decision inventory. Reconcile against an independent construct count (TDD-SRC-005).
Decision misclassification A business rule labeled technical is never tested. Classification recall test and human sampling (Section 4.5, TDD-BIZ-006).
LLM citation verifier is not fully independent Verifier may share blind spots with the drafter. Separate model or deterministic checks plus human spot-check (TDD-BIZ-007).
COBOL numeric and encoding semantics Rounding, packed decimal, and collation differences can pass ordinary tests. Dedicated fidelity tests (TDD-FUN-006 to 010).

16. Definition of Done

Source Coverage All reachable source areas are accounted for, with unreachable areas explicitly reported.
Business Logic Business rules have source traceability and verification.
Scenario Coverage Every outcome of each business-classified decision point maps to an executable scenario and meets the Section 8 thresholds.
Behavioral Equivalence Required legacy-vs-new comparisons satisfy the configured equivalence criteria.
Security Mandatory security checks pass or have an explicitly approved disposition.
Performance Configured performance requirements are satisfied where applicable.
Traceability Source → Rule → Scenario → Execution → Comparison → Decision is reconstructable.
Human Validation Required human/customer review is recorded.
Final definition The modernization is considered evaluation-complete only when the required scenarios pass, discovered decision points are accounted for, behavioral differences are resolved or explicitly dispositioned, security/performance requirements are satisfied where applicable, and the resulting evidence is available for human/customer validation.
